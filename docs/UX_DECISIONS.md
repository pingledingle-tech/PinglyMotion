# UX decisions: timeline and poser as one design

Status: agreed with the project owner on 20 November 2026. Each step starts only when the owner says start. Merged: step 1 (Start, Stop, Replay from start, Loop; pull request 251) and step 2 (Frame back and Frame forward; pull request 271). Built, open pull requests waiting for the owner's Windows test: step 3 (easing tiles, pull request 269), the timeline scrolling to the selected joint (pull request 273) and the transport buttons in the design system (pull request 275). Steps 4 to 13 are not built yet. Issue #14 tracks the work. Where this page and [POSING_UX.md](POSING_UX.md) differ, this page wins.

## General rules

- Clean screen: "you need what you need when you need it". Advanced things stay hidden until you ask for them.
- It must work on a small laptop screen and scale well on big screens and second screens. All panels and small windows can be moved, resized and popped out.
- Automate tests wherever possible (buttons exist, settings are remembered, the welcome window shows only once). The owner tests only what he sees and feels on the Windows build.
- Anything can be changed later if it turns out badly.

## 1. Transport (play buttons)

- Buttons: Start, Stop, Replay from start, Step one frame back, Step one frame forward.
- Loop on/off switch, on by default.
- Step 1 (built and approved): Start, Stop and Replay from start buttons and a Loop check box under the timeline (`src/transportbar.*`). Start can be clicked only while stopped, Stop only while playing, Replay from start always. The Loop check box and Options > Loop are the same setting, remembered between sessions.
- Step 2 (built and merged, pull request 271): **Frame back** and **Frame forward** buttons right of Replay from start, with the same look as the other transport buttons. Each goes one frame and stops at the ends, never wrapping around: Frame back cannot be clicked on the first frame, Frame forward not on the last. While playing, a click stops playing first. The left / right arrow keys do the same when no field, list or slider has the keyboard focus. Clicking a transport button does not take the keyboard focus, so the arrow keys keep working afterwards. A modern button look (Start green, Stop red, a replay icon) is a separate later item.
- Speed control: not now. Add it later if it is missed.
- Colours (the project owner, 22 November 2026): Start green (`go_fill`), Replay from start violet (`replay_fill`), Stop red (`danger_fill`), each with its icon and word. Shown in the clickable mockup; the built transport bar still has the older look until a job changes it ([DESIGN_SYSTEM.md](DESIGN_SYSTEM.md), "Shape").
- Look (built, waiting for the owner's test; redone in the design system of 21 November 2026): Start is the main button (accent colour) with a play icon, Stop a danger button (danger colour) with a square icon, Replay from start a normal button with a round arrow, all with the same shape and Lucide icons in the colour of their text, from the theme tokens in the dark and the light theme. A button that cannot be clicked is pale and says why in its tip and the status line ("It is already playing. Click Stop to stop it."). Keyboard focus shows a ring; when Start or Stop can no longer be clicked, the focus moves to the other one, so Space starts and stops. The buttons are drawn by the program (`src/transportlook.*`, icons `src/lucideicons.*`), grow with the text size and need no picture files. Texts, order and behaviour are unchanged.

## 2. Easing tiles

- Text names by default.
- The small preview picture animates only while the mouse hovers over a tile. No constant motion.
- In the clickable mockup each tile draws its curve: time to the right, the pose from a dashed Start line to a dashed End line. The part of a curve that goes past End is drawn thicker, shaded, three times taller and marked "past End", so an overshoot can be seen at once (the project owner saw only the figures and not the overshoot in his test). On hover a dot runs along the curve and a small bar on the right shows how far the pose has come.

**Built, UX phase 5 (23 November 2026):** the heading "How the move feels", a check mark on the current tile, the arrow keys in the row (Tab reaches the current tile), the reasons of a greyed-out row in its tips and the status line, and "Edit curve..." beside the tiles in Expert mode only, as in the mockup. Details: [EASING.md](EASING.md), "The row and the Edit curve window as in the mockup (UX phase 5)"; tests `tests/easingtiles`. Not built on purpose: the curve picture with the overshoot marked "past End"; showing the overshoot on the tiles is parked by the project owner (jobs list), so the tiles keep the approved figure and dot trail.

## 3. Curve editor

- Opens as a small separate window from an "Edit curve" button (on the easing tile or the selected key).
- Movable, resizable, can go on a second screen. Opens small on a laptop.

**Built, UX phase 5 (23 November 2026):** the window "Edit curve" (`CurveEditorDialog` in `src/easingtiles.*`) opens from the "Edit curve..." button beside the tiles (Expert mode). It opens small the first time, then where it was last time with its size, also after a restart, checked against the screen it lands on (`DialogFit::remember` in `src/dialogfit.*`: never larger than that screen and with its title bar inside it). The curve works with the keyboard too (arrow keys move a handle, Space picks the other one). It is modal: it edits the pose change it was opened for. Tests: `tests/easingtiles`, `tests/usersettings`.

## 4. Teaching notes (like WAVE-01 to WAVE-06)

- One thin text line under the timeline, showing the note for the current frame while playing.
- A button hides it.

**Built, UX phase 3c (behaviour and texts, 23 November 2026):** `src/timelinenotes.*` (reading the notes, the note for a frame, when the line shows, the line itself), placed under the easing tiles in `src/timelineview.*`; test `tests/timelinenotes`.

- The notes come from the file: the wave example keeps WAVE-01 to WAVE-06 ([TEACHING.md](TEACHING.md)) in its `extensions` under `"pinglymotion.exampleNotes"` (one note per key and a small task). A line break in a note becomes a space, because the line has one row of text (it wraps only when the panel is too narrow). A note in a wrong shape (no text, a frame below 0 or not whole, a second note for the same frame) is left out; at most 1000 notes of at most 1000 characters each.
- The line shows the note of the last key at or before the current frame (the first note before the first key), the same while playing and while stopped. Stopped at the last frame, at or after the last note's key, it shows the task ("Your turn: make the arm stop more softly."), as the mockup does.
- It shows only while an animation with notes is open and Help > Show hints is on. **Hide notes** (Lucide `eye-off`, tooltip "Hide the notes") hides it and the status line says "Notes hidden. Help > Show hints shows them again." (the mockup's words). Turning Show hints on again (also with the Tips switch in the status bar) brings the notes back; while the hints are already on, that means turning them off and on. Hiding lasts for this session.
- A `.dingle` file now keeps its `extensions` when it is saved (the format always said so; before this step the program dropped them), so a saved copy of the wave still has its notes.
- Left for the combined review (look, not blocking): the spacing (`spacing.s` above and below, `spacing.m` left and right, `spacing.s` between icon, text and button), the tint (`surface` with 8 percent `area_other`, the mockup's `.note`) and the `area_other` book icon, and that the line stands between the tiles' hint and the frame slider.

## 5. Timeline look

- One row per joint, diamond keys where a pose is set.
- Shows only joints that have been changed, so it stays short.
- Rows are coloured by body area, with the same groups and colours as the Joints panel tabs (Body / Face / Hands / Other).
- Colours (built, UX phase 0a, 22 November 2026): the timeline and the track names take every colour from the design tokens and follow the dark and the light theme, also when the theme is switched while the program runs; details in [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md), "Colours in the timeline and the 3D view".
- New: select a stretch of the timeline, copy it, and Paste mirrored further along (a left step becomes a right step).

**Built, UX phase 3a (behaviour and texts, 23 November 2026):** `src/timelinerows.*` (which joints have a row, the texts), `src/timeline.*`, `src/timelineview.*`, `src/timelinelook.h`; test `tests/timelinerows` (and `tests/tst_timeline.cpp`, `tests/tst_timelineview.cpp`, `tests/uxcolours` follow the new rows).

- **Rows only for changed joints** (the mockup's `editedTracks()`): a joint has a row when one of its keys holds another pose than a new animation starts with (no turn; for the Avatar Position, away from the middle of the floor or in another place than its first key), or when it has a key after the first frame that was set by hand. A joint keyed on every frame (an imported file) that never leaves the start pose has no row. The rows are in the order of the skeleton. End Sites and joints of groups left out of the lists (Options > Joints) never have a row.
- **The picked joint always has a row**, after the changed joints when it has not changed itself, so picking a joint without keys scrolls the timeline to it the same way as any other joint (the owner's test note "Timeline scrolling is not consistent for joints without animation"). Turned, it moves to its place in the skeleton order; another joint picked, its row goes again.
- **Body area per row:** each row has a 4-pixel stripe in its area colour (`area_body`, `area_face`, `area_hands`, `area_other`, the same tokens and groups as the Joints panel's tabs; the Avatar Position is on Body, as in the Joints list), the joint's name with 9 percent of the area colour behind it, the area's name on the right in `text_muted`, and the key row with 5 percent of the area colour. Keys and the lines between them are drawn in the area colour; the picked joint's row keeps `selection` with `on_accent`. The rows show the joints by the names the Selected joint panel uses, which tell left and right apart ("Left Arm: Collar"); the name column is as wide as the widest name with its area name, at least as wide as before.
- **Set key** is the blue main button of the timeline panel (`accent`, `on_accent` text, Lucide `diamond-plus`), right of the frame slider. It does what Edit > Set key and K do: it sets a key for the picked joint at this frame and never takes a key away (the old key button took the key away on a second click; Delete in the timeline still does). The status line says "Key set at frame N for <joint>." (frames counted from 1, as in the frame field), or on a frame that has a key already "This frame has a key already. Turning the joint changes it." It is greyed with the reasons of Edit > Set key, also in the reason line.
- **Empty states:** with no changed joint the timeline shows "No keys yet", the line "Set a key to save your first pose." and the main button "Set the first key" (the same as Set key, greyed the same way). While no animation is open the rows give way to "The timeline shows your keys over time. Open an animation first."
- **Keyboard:** with the timeline focused, Up and Down pick the row above or below (as a click on it); Set key and Set the first key are reached with Tab and pressed with Space; K sets a key while the 3D view has the keys.
- **Differences from the mockup, on purpose:** Set key stands right of the frame slider instead of at the end of the transport row (the program's transport row breaks into two lines in a narrow panel; this kept it on one place). The rows keep the program's row height and its key shapes; the mockup's diamond keys, ruler, loop band and marker triangle, and the look (row height, spacing), are for the combined review. A key the user sets without turning, on frame 1 only, does not count as changed (frame 1 always has a key), so "No keys yet" stays until a joint is turned or keyed later. The mockup puts the Avatar Position on Body too; the Selected joint panel's chip says Other for it (phase 2b), which is not changed here.

**Built, UX phase 3b (behaviour and texts, 23 November 2026):** `src/timelineclip.*` (the copied stretch, paste, the left-right swap, the texts), `src/timeline.*` (the selection), `src/timelinelook.h`, `src/panelcontent.h`, `src/transportlook.cpp`, `src/pinglymotionwindow.cpp`; test `tests/timelineclip`.

- **Select a stretch:** Shift and a press on an empty place of the rows starts a box there; dragging moves its far corner, and a second Shift click moves the far corner to the click. The box covers the frames and the rows between its two corners. With the timeline focused, Shift and the arrow keys grow or shrink it (it starts at the picked joint and the current frame): Left and Right by one frame, Up and Down by one row. The current frame follows the far corner. A plain click (it picks a joint, as before) or Escape leaves the stretch; opening another animation does too. The status line says "Selected frames 4 to 9 on 2 joints. Ctrl+C copies them." (frames counted from 1, as in the frame field). Shift and a press on a key still copies the key by dragging it, as before.
- **The box:** `selection` at 22 percent over the stretch with a 1 pixel `selection` border (`TimelineLook::selectionBox`); how it looks is for the combined review.
- **Copy (Ctrl+C)** keeps, for each joint of the stretch, the keys inside it and the pose at its first and last frame as keys when no key stands there, so the pasted stretch plays the same as the copied one. With no stretch selected, Copy takes the current frame on every joint that has a row (like the old Copy, which took the whole frame). "Copied frames 4 to 9 of 2 joints." or "Copied frame 4 of 1 joint."
- **Cut (Ctrl+X)** copies the same, then takes the keys inside the stretch away; every joint keeps its key on frame 0. It no longer removes the frame from the animation (the old Cut shortened the animation by one frame). "Cut frames 4 to 9 of 1 joint."
- **Paste (Ctrl+V)** puts the copied keys back from the current frame on, on the same joints, with their easing. The Mirror switch does not change it. "Pasted at frame 15 on 2 joints."
- **Paste mirrored (Ctrl+Shift+V,** Edit menu, and a button right of Set key in Expert mode, Lucide `flip-horizontal-2`, as in the mockup) puts them on the joint of the other side (left thigh keys on the right thigh, and the other way round), with left and right swapped in the pose: the same rule as Tools > Mirror and Flip, a turn keeps X and turns Y and Z round, the Avatar Position turns X round. A joint with no other side (hip, spine, neck, head) gets its own keys swapped in place. So a copied left-leg step pasted mirrored further along is a right-leg step. "Pasted mirrored at frame 15 on 2 joints. Left and right are swapped."
- Keys that would go past the last frame are left out, and the status line adds "1 key went past the last frame and was left out." or "3 keys went past the last frame and were left out." The copied stretch keeps the joints' names, so it can be pasted into another open animation too. It is not kept after the program closes.
- **Greyed with a reason** (charter P6), in this order: Paste and Paste mirrored "Open an animation first.", "Copy a stretch of the timeline first (select keys, then Ctrl+C)." (the mockup's words), "Stop playing first.", and on frame 1 with Lock the first frame on, the Set key reason about the locked first frame. Copy and Cut: "Open an animation first.", "Stop playing first.", "Nothing to copy yet. Set a key first." (no rows).
- **Not in this step:** Undo is not built yet (Edit > Undo is greyed with its reason), so a paste is taken back by hand or by Cut. The finger joints use the same swap as the rest of the body, which is also the Hands tab's copy rule (6i, built in phase 2c). The Paste mirrored button shows only in Expert mode, as in the mockup; the Edit menu item and Ctrl+Shift+V work in both modes.

## 6. Selected joint panel

- Order from the top: joint name (and SL name), Reset, rotation sliders X/Y/Z showing the allowed range, limit warning.
- Advanced things (IK, lock, move) further down.
- Joint limits are a helper, not a wall: they warn, and can be switched off. SL has no limits, so strange poses on purpose must be possible.
- Self-explaining for beginners, as shown in the clickable mockup: the joint name with its body-area chip and key count; one plain line that says how to turn it (sliders or rings, then Set key); each slider has its axis badge (X red, Y green, Z blue) and a plain name ("Tilt forward or back", "Turn left or right", "Lean to the side"), the allowed range under it and the number in degrees; near a limit the slider says so and a warning card names the axis and offers "Turn limits off". "When you drag this joint in the 3D view" is a plain choice between "Pull the limb" (IK, explained in one line) and "Turn only this joint". Lock, Move and "Turn around the axes of: Joint / Avatar / Screen" fold away under **More options**, in both modes.

**Built, UX phase 2b part 1 (values and texts, 23 November 2026):** `src/selectedjointpanel.*`, tests in `tests/selectedjoint` and `tests/uirender` (mainpanels). The panel has three pages: "Nothing to turn yet" (no animation open), "Pick a joint" (three steps and "Pick the right shoulder for me", which picks `rShldr`), and the joint. The joint page has the name, the body-area chip, the key count and the Second Life name; the hint line (with hints on); X red, Y green, Z blue sliders with their letter badge, plain name, number in degrees and the range line ("-90°  allowed range  90°", or "no limits"); the arrow keys turn one degree, Page Up / Page Down ten. Near a limit (closer than 6 percent of the range to an end, as the mockup) the name says "(near its limit)" and the warning card names the axes and offers "Turn limits off". The switch "Warn near the joint's limits" is the same setting as Options > Stop joints at their furthest turn (`joint_limits`), so the sliders still stop at the limits while it is on. Reset joint puts the joint back as it is in the first frame (greyed "This joint is not changed." when it is). While playing or on a locked first frame the sliders, fields and Reset joint are greyed with the reason, also in the status line. More options (folded at first, remembered as `joint_more_options`) holds Change: Turn / Move; Move works only for the pelvis and the Avatar Position (the Avatar Position only moves). The look (spacing, sizes, the switch drawn as a switch) is the second pull request of phase 2b and goes to the combined review.

Differences from the mockup, on purpose (true texts for what the program does today):
- Since UX phase 4b part 2 "Pull the limb" / "Turn only this joint" and "Pull with keys" work (6a). Their caption is the mockup's with shorter sentences: "The joints above it bend, so the limb follows your pointer. This is called IK." (the mockup's first sentence has 16 words, over the 12-word limit, so "like pulling a puppet's hand" is left out), and the Pull with keys tip says "Pick the joint up and move it with the arrow keys. Enter sets a key. Esc cancels." (the mockup's first sentence has 15 words). (Before part 2 they were greyed with "Pulling the limb comes in a later version.")
- The hint line and the third "Pick a joint" step say that turning sets a key ("Turning it sets a key."), because the program keys a turn at once; the mockup's "Press Set key" and "the rings in the 3D view" (phase 4b) are left out. The first step says "Click a joint on the figure, or in the Joints list." (the mockup's has 13 words).
- No "Changed, not a key yet" chip (a turn is a key at once), no Lock and no "Turn around the axes of" (nothing in the program does them yet); the More options caption says "turn or move". The Change choice says Turn / Move (the glossary word, not "Rotate").
- The limits switch's tip says "Second Life has no limits. Turn them off for odd poses on purpose." (the mockup's "Limits only warn" is not true: the sliders stop at the limits while it is on).
- Move has its own names: "Left or right", "Up or down", "Forward or back", and no degrees.

## 6a. Dragging a joint in the 3D view

Shown in the clickable mockup (`docs/mockup/index.html`); approved as UX phase 4b part 2 in the jobs list (issue 74) and built (below).

- Click a joint to pick it. Press on a joint and drag to **pull the limb**: the joints above it bend so the limb follows the pointer (IK pull). One gesture does both: pressing an unpicked joint picks it and pulls it.
- While dragging: a grabbing cursor, a dashed line from where the joint was to the pointer, the pulled limb highlighted, and a small label next to the pointer that says what is happening ("Pulling Right Hand", "Release: set key, Esc: cancel"). The hint bar says the same.
- **Release** sets the key at the current frame for the pulled joints. **Esc** during the drag cancels, nothing changes. **Ctrl+Z** undoes the whole pull in one step.
- **Pull or turn only:** the IK switch in the Selected joint panel (on by default) chooses what a plain drag does. Holding **Shift when you press** the joint does the other one. "Turn only this joint" swings that joint so its own bone follows the pointer. The pelvis and torso have no limb above them, so they only turn.
- **Keyboard alternative:** with a joint picked and the 3D view focused, **Enter** (or G) picks the joint up, the **arrow keys** move it (Shift: small steps), **Enter** sets the key, **Esc** cancels. The "Pull with keys" button in the Selected joint panel does the same. Shift + Enter picks it up in the other mode.
- First-run hint "Pull a limb" (after "Pick a joint"); it is also in the Camera and keys card and the Keys and mouse list.
- The ring and the sliders still turn a joint without keys being set until Set key, as before.

**Built, UX phase 4b part 2 (dragging a joint; 23 November 2026):** `src/limbpull.*` (which joints bend, the chain and the solver, without a screen), the 3D view (`src/animationview.*`: the press, the drag, the keys, the picture), the window (`PinglyMotionWindow::pullFinished()`), the texts in `src/viewtoolspec.h`, `src/selectedjointpanel.h`, `src/camerahabitspec.h` and `src/keysmousedialog.h`. Tests: `tests/limbpull` (exact angles of defined pulls), `tests/viewtools`, `tests/selectedjoint`, `tests/camerahabits`, `tests/setupdialog`.
- **Which joints bend:** up to three joints above the pressed one, nearest first (the mockup's `limbAbove(id, 3)`), never the hip; a classic joint passes over the Bento-only bones between them (mSpine1 to mSpine4), a Bento joint (a finger, mFootLeft) counts every joint above it. So the right hand bends the forearm, upper arm and collar; the left foot the shin and thigh; the head the neck, chest and abdomen; the chest the abdomen. The hip and the abdomen have nothing above them: a drag turns only them, and the label says "Turning only Abdomen (it holds the body)".
- **The solver** is the mockup's `solveIK()`: on every mouse move 14 rounds, each driven joint in turn (nearest first) turns on X, then Y, then Z by the step a one-degree test turn says brings the joint closest to the pointer, times the joint's weight (1, 0.6, 0.35), at most 20 degrees per step, inside the joint's limits while Options > Stop joints at their furthest turn is on (with the limits off, up to 180 degrees). It starts each move from the last move's turns, so the limb follows the pointer over a drag. One addition on purpose: a little damping (0.05 inch per degree, `LimbPull::damping`), so an axis that only twists a straight bone does not spin by 20 degrees at each step (the mockup has almost none). A joint already turned past a limit keeps that turn as the end of its range for the pull, so the pull never snaps it back. The pointer's place is found on the screen at the joint's own depth.
- **The press:** with Pick and pull (V), pressing a joint (its dot or the body around it) and moving 5 pixels starts the pull; a press on an unpicked joint picks it first. A press on empty space still turns the camera in the PinglyMotion habit; in the PinglyMotion habit a drag on the body now pulls the joint under it instead of turning the camera. Shift when pressing does the other one of the drag choice ("Pull the limb", the default, or "Turn only this joint"; `pull_limb_on_drag`). Turn only swings the joint so its own bone (the point where its first child is) follows the pointer.
- **While dragging:** a grabbing (closed hand) cursor, a dashed line (6 on, 4 off) from where the joint was to the pointer with a ring of 12 pixels and a dot at its end, the pulled limb drawn in accent_text (the bones thick, the body parts coloured), and a label next to the pointer: "Pulling Right Hand" (or "Turning only ..."), "Release: set key · Esc: cancel" and, for a mouse pull of a limb, "Shift when you press: turn only this joint". The hint line (the status line, while Help > Show hints is on) says the same in one line. The animation is not changed until the release: the picture shows the pull's turns on top of it.
- **Release** sets a key at the current frame for each joint that bent (a turn is a key at once, as with the sliders; the pulled joint itself gets no key in a limb pull), and the status line says "Pulled Right Hand. Key set at frame 5 for Right Forearm, Right Upper Arm, Right Collar and Right Hand." (Turn only: "Turned Right Forearm. Key set at frame 5 for Right Forearm."). **Esc** cancels: nothing changes, "Pull cancelled. Nothing changed." While a pull runs every other key waits; Ctrl with a key says "Finish or cancel the pull first: Esc cancels."
- **Keyboard:** with a joint picked and the 3D view focused, Enter or G (or the Selected joint panel's Pull with keys) picks it up; the arrow keys move it 12 pixels on the screen (Shift: 3); Enter or Space sets the key; Esc cancels. Shift + Enter picks it up the other way than the drag choice. Without a joint: "Pull with keys: Pick a joint first. Click it on the figure or in the Joints list."
- **When it cannot start** (the same reasons as Set key): "Pull a joint: Stop playing first." (with the keys "Pull with keys: ..."), "Open an animation first.", and the locked first frame's reason.
- Hovering a joint with Pick and pull says "Click to pick this joint. Press and drag to pull the limb." (the mockup's HINT-02). The first tool is now "Pick and pull" (6b). The Camera and keys dialog and Help > Keys and mouse list "Pull a limb", "Turn only that joint" and "Pull with the keyboard" (the mockup's rows).
- **Differences from the mockup, on purpose:** Undo is not built yet, so Ctrl+Z does not undo a pull and the status line leaves out "Ctrl+Z undoes it."; save a copy before big changes, as Edit > Undo says. The first-run hint "Pull a limb" comes with the guidance step (phase 6). The Pick and pull tip leaves out the mockup's "Drag empty space to look around.", which is true only in the PinglyMotion habit. Pressing the body (not only a joint dot) pulls the joint under it, because the program's body is picked joint by joint; Bento dots near the pointer win as in picking (so a press next to the wrist may grab a finger). The old IK (Ctrl + double-click, which holds a hand or foot in place) stays as it was.
- **For the next combined review (feel, not blocking):** how the pull feels (speed, smoothness, whether it lags behind the pointer or overshoots; the 14 rounds, the weights 1, 0.6 and 0.35, the 20-degree largest step and the damping are the values to tune), whether the torso should bend as much when an arm is pulled (a forearm pull also bends the chest, the third joint above it), whether the label and the dashed line are in the right place and size, the 12- and 3-pixel arrow key steps, and how the ring letters and the faint back half look.

## 6b. Rotation rings and the view-direction widget

Shown in the clickable mockup (`docs/mockup/index.html`); approved as UX phase 4b in the jobs list (issue 74). Part 1 and part 2 are built (below).

- Three rings, red X, green Y and blue Z, are drawn around the **picked** joint (never around another joint), in the frame of its parent. Dragging a ring turns the joint on that axis only; Shift gives fine steps. Each ring carries its letter. The back half of a ring is drawn faint. Hovering a ring thickens it and the hint bar says "Drag the red X ring to turn the joint: tilt forward or back".
- Top left of the 3D view: a round **view-direction widget** like Blender's navigation gizmo, with coloured X, Y, Z ends that turn with the camera. Clicking an end looks from there (front, back, left or right side, top, below); dragging the widget turns the view. With the keyboard the ends are reached with Tab and arrow keys and chosen with Enter. The current view's name is under it.
- Under it a vertical **view toolbar** with names and keys (names can be switched off in its Show menu; a short 3D view gets a two-column icon toolbar): what the left mouse button does (Pick and pull V, Look around O, Move the view M, Zoom Z, the active one marked with a bar and a frame), framing (Picked joint F, Whole figure Shift+F, Home view 0), **Look from** (Front, Side, Top, Back; also in the View menu and on Numpad 1, 3, 7) and **Show** (floor grid, rotation rings, joint dots, tool names).

**Built, UX phase 4b part 1 (view toolbar, view-direction widget, view name, ring hint; 23 November 2026):** `src/viewtoolbar.*` (the toolbar), `src/viewgizmo.*` (the widget), `src/viewtoolspec.h` (every text, checked word for word against the mockup), `ViewTool`, `ViewName`, `Camera::gestureFor(habit, tool, ...)`, `Camera::toolForKey()`, `Camera::viewNameFor()` and `Camera::lookFrom()` in `src/camera.*`; the window wires it in `setupViewToolbar()`.
